## 主题记录

写在 `refs/cards/decisions/<topic>.md`。用简短英文 slug 保留链接稳定性，主题用中文标题并注明日期与状态。先写当前选择和理由，再写症状、现版基线（链接到代码、规格或试玩）、约束、候选比较与触发下一步的条件。状态可用「待补证据 / 待试验 / 已试验 / 已采纳 / 暂缓」，已试验时附结果，已采纳时链接正式设计位置。

每个候选用三级英文标题保证稳定锚点，例如 `### outcome-feedback`，正文第一句写清要做什么。

| 维度 | 填写内容 |
|---|---|
| 做法与适用场景 | 一到三句说清玩家动作、触发条件、反馈或机制、预期作用 |
| 证据与边界 | 指向来源编号，交代原文讲了什么、做法的成熟度、什么还需要本作验证。把冲突与反例留在卡上 |
| 本作映射 | 哪些已有、部分已有、缺失或待核实，以及要复用的节点、数据或契约。明确本作推断 |
| 代价与依赖 | 程序、美术/音频、内容、系统复杂度与交付依赖。无实测工时用相对量级或写待估 |
| 最小验证 | 基线、只改的变量、场景和观察项、通过与回退条件。区分技术 smoke 和体验判断 |

最后附来源表。用 `S1`、`S2` 等稳定编号标识作品/作者、平台、原链接、日期或版本、实际读取范围及定位（时间戳、章节、页码、代码路径）。无法核实的字段写「未记录」或「待核实」。较长的抽取说明可放 `<details>`，大段原文、完整转写或媒体保留在原处。

新增主题时更新上方索引。已有相同操作含义的机制时，给原卡补证据、保留旧锚点与人工备注。若两做法在不同条件下能独立验证，把卡和各自的条件都保留下来。
