# 2026-11-17-01 火焰/热：Noita vs 我的世界，及我们的借鉴与排期

- 日期：2026-11-17
- 作者：DeepSeek
- 类型：建议（研究 + 方案）
- 篇幅：详细
- 触发：用户问「这个火焰 Noita 和我的世界是怎么处理的？如何借鉴？还是说留到下一阶段解决？」

## 结论

1. **Noita 的火不是系统，是材料**：火是材质（3 种颜色变体）、不同材质燃烧速度/产物不同；生物有「点燃」状态（2% 最大生命/秒、移速 +15%、恐慌）；水/黏液灭火、油/威士忌助燃、潮湿防点燃；燃烧产生烟（窒息）；水+火→蒸汽；「热源 + 可燃材料」作为反应传播；爆炸/岩浆也是热源。
2. **我的世界的火是「会老化的方块」**：age 0–15、每 1.5–2 秒调度 tick；3×3 水平 + 上 4/下 1 格传播；点燃概率 = 基础值 + age + 难度 + 相邻可燃性；无燃料就熄；ignite/burn odds 按方块；水/雨灭火；生物有 Fire 计时 160 ticks 持续燃烧；**只更新玩家 8 区块内的火**（性能门槛）。
3. **我们的借鉴**：取 Noita 的「材料化 + 反应表驱动 + 烟/蒸汽/潮湿」，取我的世界的「老化/熄灭条件 + 数据化点燃概率 + 邻近更新预算 + 可预测规则」；不做全局逐格温度场，不做照抄数值/代码。
4. **排期：留到 M1**（反应表阶段），M0 不扩 scope。理由：火必须与反应表执行器一起做才有意义（`data/materials.json` 的 8 条反应、3 条 heat 阈值、`temperature/ignition_temperature` 字段现在都还没有引擎消费）；会改 C-SIM 语义和性能预算，而目标机基准还没测；M0 只回答「跑得动/语义清/好不好玩」。T4b 的火是灰盒占位，够支撑实验 C 的组合时刻。
5. **顺带查出一个事实**：T4b 里只有**油**会自燃；煤/硫/竹木的 `flammable=true` 已进材质表，但 `ignition_temperature`（300/250/200）引擎没读，点燃概率为 0——所以「瓦斯囊」现在只是色块，不会烧/冒毒烟。这不是 T4b bug，是 M1-12 的工作。

## 决定与理由

| 决定 | 为什么 | 代价 |
|---|---|---|
| 火/热留到 M1（不现在做） | M0 时间盒只剩收尾（目标机复测 + 试玩），扩火系统会动 C-SIM 语义/性能且无法在目标机验证；火必须配反应表才有意义 | T4b 的「瓦斯囊」暂时不真烧；用户可能觉得假（已写入已知限制） |
| 采用「热源 + 邻域阈值」而非全局温度场 | 逐格温度是性能/复杂度陷阱；我们的数据已有 `temperature/ignition_temperature/heat 反应`，局部判定就够表达「可读因果」 | 没有热传导/余温等细腻效果（M2+ 再评估） |
| 借我的世界的「邻近更新」性能门槛 | 和我们的 chunk 活跃区天然契合；全屏燃烧是性能风险点（D4 预算 6ms/2ms） | 视野外的火冻结不演化（与现有 active rect 一致） |
| 借 Noita 的实体「点燃/潮湿」状态 | 比固定伤害更可读、可组合（水/油/酒都能影响）；M1-02 战斗直接复用 | 需要实体状态 + C-EVT 事件，属 M1 契约工作 |
| 明确不照搬 | 项目红线：不照搬 Noita 代码/数值/资产；MC 的固定网格/难度公式/无限燃烧也不适用 | 需要自己配 `burn_time/burn_product` 等数据（M1 计划里定） |
