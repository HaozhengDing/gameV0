## 结论

- 开发分 5 步，每步只回答一个问题、以一道门结束：M0 能不能做 → M1 一层好不好玩 → M2 垂直切片 + Demo → M3 生产到 EA → M4 EA 到 1.0。
- 流程借鉴：阶段门 + 风险驱动 + 固定时间可变范围（Shape Up）+ 契约先行 + WIP 上限 + 关键路径。
- 依赖只连产物（文件），分硬 / 软（可打桩）/ 决策 / 门四类；多数依赖指向 7 个契约（C-DATA / C-VM / C-ACT / C-SIM / C-EVT / C-TEXT / C-SAVE）。
- 用这套规则重看 M0：关键路径是 T2 → T4b → T5；T4 拆出 T4a 在 W3–W4 用桩先踩构建链的坑。

## 决定与理由

| 决定 | 为什么 | 代价 |
|---|---|---|
| 5 步而非设计原文的 4 步 | 原文按 4–6 人排期，M1 直接做三大系统；个人 + AI 需要先有"一层完整循环"的门，再做对外的垂直切片；EA 之后单列 M4，命格在此回归（D5） | 量级只能占位，每道门都要重估 |
| 依赖只连产物 | "感觉要等"的依赖说不出文件就不是依赖，可以并行；这是拆乱麻最直接的办法 | 每个任务都要多写输入 / 输出两栏 |
| 依赖分四类 | 硬依赖要排队，软依赖能打桩，决策依赖卡在用户身上，门依赖卡在评审上；混在一起就看不出谁真正在等谁 | — |
| T4 拆出 T4a（W3–W4） | 关键路径 T2 → T4b → T5 没有余量；Godot + GDExtension 构建链是常见集成坑，用桩提前踩掉 | W3–W4 多一条 AI 并行线 |
| T1 增加 C-ACT（动作列表格式） | 原计划里 VM 输出的动作由谁在世界里执行没人负责，是 T3 与 T4 之间的缺口 | T1 规格多一节 |
| 用户注意力设 WIP 上限（同时待决 ≤ 2 件） | 瓶颈是用户的审阅与决定，不是写代码 | AI 有时要先做次要任务 |
