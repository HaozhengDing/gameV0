## T0｜数据校验脚本 + CI

**是什么**：`tools/validate_data.py` + `.github/workflows/validate.yml`，每次 push 自动检查数据与卡片的引用是否一致。

**为什么**：这次设计收敛里发现的问题——黑火药被定义了两次、旱魃弱点写五行、卡片残留旧数值——都是靠人工 grep 找到的。之后多个 agent 并行改数据，只有让机器检查才靠得住。

**检查项**：

- 所有 JSON / YAML 能解析
- 反应：`inputs` 与 `consumes` 都是已定义的物质；`consumes ⊆ inputs`；`priority` 为整数
- biome：hazard 的 `reaction` 存在，`materials` 存在；boss 的 `weak_to` 是已定义的物质
- room：`rule_id` 在所属 biome 的 `rules` 里存在；`hazards` 在 biome 里存在
- `magic_numbers.json`：必需的键都在（如 `economy.silver_base`、`sanity.possession`）

**完成标准**：当前仓库通过；故意改坏一个引用时，CI 变红。

**代价**：每加一种新数据，就要同步补校验规则。

## T1｜符箓 VM 形式规格 + 30 条用例（实验 B 前半）

**是什么**：`docs/tech/talisman-vm-spec.md` + `tests/vm_cases/*.yaml`。先写规格和期望结果，再写实现。

**规格必须回答**（批注 C06 / C09 / C46）：

1. 基本单位：符、句、轮、回符分别指什么
2. 抽牌游标怎么走；乱序作用在符这一级还是句这一级
3. 连续符脚归属哪个符胆；一句里有多个符胆时，符头状态如何共享
4. 触发类符头（敕·触、奉·时）的递归：深度上限（建议 3）、单次动作上限（建议 64）、投射物上限（建议 32）
5. 灵力不足时：整句不念，还是念到哪算哪；何时扣灵力
6. 无效句（有符脚没符胆）怎么处理
7. 禁符反噬、幻符替换、幻影符（S-0004 `phantom_rules`）在 VM 中的确切时序
8. **动作列表格式**（契约 C-ACT）：VM 输出什么样的动作、由谁在世界里执行（生成投射物、生成物质、改状态）。这是 VM 与 T4 之间的接口

**用例格式**：输入法器 + 符序列 + 初始状态 → 期望的动作列表与资源变化。30 条中至少 5 条覆盖禁符 / 幻符，至少 5 条覆盖触发递归与上限。

**完成标准**：你审过规格；30 条用例的期望结果没有歧义。

**代价**：W1–W2 看不到"会动的东西"；但没有这份规格，T3 和 T4 的实现会各写各的。

**2026-11-15 进度**：草案 v0.1 已出（8 问全答 + C-VM/C-ACT/C-CASE + 30 条用例，自检通过），顶部标「待用户审定」。用户审定前 T3 先按草案实现并回归；审后若改语义，先改用例再改实现。6 条已由用户 2026-11-16 **全部拍板**（按 AI 建议：#1 句、#2 预付费、#3 整句不念、#4 归 cost 0/返还 8、#5 3/64/32、#6 Option B），spec v0.1 视为冻结候选，后续若改语义先改用例再改实现；T3 复审还补了 §7.4.1 六条边界口径（见 docs/log/2026-11-15-09-t1-vm-spec.md、-10、-11、2026-11-16-01/02）。

## T2｜`sim_core` 最小原型 + 基准测试（实验 A）

**是什么**：一个不依赖引擎的模拟库，加一个无界面的基准测试程序；不做刚体碎裂，不做多线程（D4）。

**技术选择（已定）**：**C++17 + CMake**。

- 理由：Godot 官方的 GDExtension 绑定是 C++（godot-cpp），T4 接入时路径最短；AI 写 C++ 的语料也最多。
- 代价：内存安全要靠纪律和 sanitizer。
- 例外：如果你更熟 Rust，T2 开工前改选 Rust（Godot 用 gdext 绑定）。只能在开工前改。

**步骤**：

1. 格子与 chunk（64×64）+ 脏矩形；物质类型分粉末 / 液体 / 气体 / 静态
2. 5 种物质：沙、水、油、火（带寿命的燃烧状态）、水银（密度大于铁）+ 挖掘
3. 从 `data/materials.json` 读物质参数（沙和油作为实验物质另加）
4. 基准场景：最坏场景（整屏 480×270 全是流动物质）和典型场景（矿井灰盒，载入 3×3 屏）；固定种子跑 10,000 tick
5. 输出 p50 / p95 / p99，每 1000 tick 导出一帧 PNG 供目测

**完成标准**：在目标机上产出 `docs/tech/m0-a-report.md`。对照通过标准：最坏场景 p95 ≤ 6 ms，典型场景 p95 ≤ 2 ms。不过时按 D4 先把格子加粗到 2×2，再重测。

**代价**：这是整个 M0 技术风险最高的一项，也是最可能超时的一项。超过 W5 仍未出报告，就把 T4b 改为基于粗格版本推进。

**2026-11-15 进度**：原型 + 基准程序 + 5 个 ctest 已完成，开发机数字（worst p95 2.245 ms / typical p95 0.145 ms）全部过 D4 线，但**不构成实验 A 通过**——按 D4 必须在目标机复测，报告 §7 已写好复测命令与判定线；目标机后移期间报告标「开发机数据，非 go/no-go 依据」（见 docs/log/2026-11-15-08-t2-sim-core.md）。

- **T4b（W5–W7）**：接入真 `sim_core` 和 VM，做内容。

**2026-11-16 进度**：T4b 可玩灰盒完成——Godot 灰盒（960×540 矿井、data/rooms 两房间按 tile_size=16 展开、走廊+火障+出口）、P0 四组符经真 VM 施法、葫芦吸/喷水油；组合时刻「化水银→取水→灭火→通关」由 `--t4b-smoke` 脚本化验证通过（exit 0）。为接入房间数据 C-SIM 升 v2（append-only 9 种 data 物质），新增 `data/talismans.json` 正式卡表 + 校验；截图 `docs/tech/t4b-graybox-2026-11-16.png`，记录见 docs/log/2026-11-16-04。用户本机试玩手感反馈待收集（T4b 不判 go/no-go）。

**T4b 是什么**：通过 GDExtension 接入 `sim_core` 和 VM，做出 10 分钟的可玩内容：

- 角色移动 + 挖掘
- P0 的 4 组符（`refs/cards/p0/talismans.yaml`）+ 葫芦（先只支持水、油两种液体，批注 C07）

**不做**：神智、入魔、洞天、旱魃完整战斗、水墨后处理。

**完成标准**：你自己能在 10 分钟内玩完一轮，并且至少经历一次组合生效。

## T5｜10 分钟试玩

**是什么**：5 名外部玩家各玩 10 分钟，不给任何讲解；你只观察、记录。

**流程**：

1. 试玩前不解释任何机制
2. 记录：第一次尝试组合的时间、卡住的位置、自言自语
3. 试玩后只问两个问题：「刚才发生了什么？为什么？」「你还想试什么？」

**通过标准**（D4 实验 C）：≥ 3 / 5 人在 10 分钟内自发完成一次"用符改环境 → 环境改法术"，并能复述因果。

**产出**：`docs/tech/m0-c-report.md` + 一篇 log。
